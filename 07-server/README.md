# labeled — сервер API

Node 24 + Fastify 5 + Postgres (Drizzle ORM). Одна база и одно API для покупателя (Mini App) и режима администратора (adm01–adm34). Ответы — в тех же типах, что уже использует приложение `06-app` (`CatalogItem`, `Product`, `Order`, `Payment`, `AdmPayment`, `AdmOrder`…): типы и правила расчёта импортируются из `../06-app/src/domain` и `../06-app/src/admin/model`, а не копируются.

Состояние на 2026-10-08: сервер покрыт тестами API (88 тестов на 2026-10-09; аудит — `../01-project/quality-audit-2026-10-08.md`), приложение `06-app` подключено к нему (режим `VITE_API_URL`, сквозная проверка `06-app/scripts/check-live.mjs` — 64 проверки). С 2026-10-08 работает на FirstVDS с Postgres 16 — `https://<IP-через-дефисы>.sslip.io`, устройство и выкладка — `deploy/README.md`. На устройствах в Telegram ещё не проверялся.

## Запуск

Node установлен в `~/.local/node` (не в PATH). Кеш npm — `~/.local/npm-cache` (в `~/.npm` нет прав).

```sh
export PATH=~/.local/node/bin:$PATH
export npm_config_cache=$HOME/.local/npm-cache
npm install
npm test                         # 60 тестов API на PGlite в памяти
npm run typecheck
SEED_DEMO=1 npm run dev          # http://localhost:8787, база PGlite в ./data/pglite, демо-данные
npm run build && node dist/main.js
```

Без `DATABASE_URL` сервер берёт **PGlite** — настоящий Postgres, собранный в WASM, внутри процесса (папка `PGLITE_DIR`, по умолчанию `./data/pglite`). Postgres и Docker на этой машине не установлены. В продукте — обычный Postgres по `DATABASE_URL`; миграции из `drizzle/` применяются при старте.

Проверка без Telegram: заголовок `x-dev-user: 1001` (Анна, покупатель), `2001` (Иван, владелец), `2011` (Ксения, менеджер), `2012` (Артём, склад), `2013` (Лиза, контент). Работает только вне `NODE_ENV=production` и без `BOT_TOKEN` (с токеном — только при явном `DEV_AUTH=1`); `DEV_AUTH=0` выключает всегда.

## Вход и права

- Приложение шлёт `Authorization: tma <initData>`; подпись проверяется токеном бота (`@telegram-apps/init-data-node`), срок — `INIT_DATA_TTL`.
- `POST /api/session { consent }` — вход (BA, P). Новый покупатель создаётся только с согласием с офертой и политикой; иначе `401 consent_required`. Параметр запуска `ref_<tgId>` запоминает пригласившего, `staff_<код>` принимает приглашение сотрудника.
- Режим администратора: сотрудник — строка `staff` у пользователя. Права роли (`06-app/src/admin/model.ts`) можно переопределить; курс, реквизиты и сотрудники — только владелец. Права проверяются на каждом запросе `/api/admin/*`.
- Каждое действие сотрудника пишется в `journal` (кто, когда, что) в той же транзакции. Журнал (adm33) читает только владелец: `GET /api/admin/journal?who=<id сотрудника>&type=<pay|req|orders|stock|catalog|prices|staff>` — последние 300 записей за 12 месяцев с текстом, объектом и экраном объекта (`src/services/journal.ts`).

| `products`, `offers` | Модель вещи с расцветками и фото; предложения — конкретные экземпляры с состоянием, размером, ценой и остатком (0 — не видно). |
| `favorites`, `size_requests` | Избранное; заявки на отсутствующий размер (7p → adm31: «Размер есть» / «Отклонено»). |
| `orders` | Заказ из наличия (`stock`) или по ссылке (`link`). `phase`: review → changed → invoiced → active → done, ответвления rejected/cancelled. `stage`: 4 точки наличия или 8 этапов продавца. Суммы и параметры курса фиксируются в заказе. Отмена продавцом — причина и сумма к возврату, отметка «деньги возвращены». |
| `order_items` | Позиции: предложение и цена в ₽ (наличие) или ссылка, размер, цена в ¥, услуги, старая цена и «убрано продавцом» (заявка). |
| `order_history` | История для D и даты этапов в adm10. |
| `parcels` | Посылки: состояние, трек CDEK, вес после взвешивания, с какого момента ждут трека. |
| `payments` | Переводы: `p-1041` за товары, `p-1042-1` за доставку посылки. empty → review («Перевёл») → ok / fail; чек покупателя и чек продавца. |
| `link_drafts` | Черновики заказа по ссылке. |
| `photo_reports` | Фотоотчёт со склада: фото по каждой вещи, отправлен ли. |
| `claims`, `claim_messages` | Обращения: причина, фото, переписка, решение, сумма и реквизиты возврата. |
| `reviews` | Отзывы: модерация mod → pub / hid. |
| `points_ledger` | Каждое движение баллов; награда за друга — один раз на друга (уникальный индекс). |
| `events` | События покупателя (N) и отметка об отправке ботом. |
| `journal` | Журнал действий сотрудников (adm33). Только добавление: правку, удаление записи моложе 12 месяцев и TRUNCATE запрещает триггер базы (миграция `0003_journal_immutable.sql`); старые записи удаляются при запуске сервера и при чтении журнала. |
| `settings` | Курс, ступени надбавки и комиссии, услуги, реквизиты, техработы и мин. версия, документы. |
| `files` | Загрузки: чеки, фото товаров, фотоотчёты, фото обращений и отзывов. Тип проверяется по первым байтам. Приватные файлы — по подписанной ссылке на сутки (картинки в WebView без заголовков). |

## Правила, которые держит сервер

- **Заказ из наличия**: цена и остаток сверяются под блокировкой строк (остаток — с суммой всех строк одной вещи); изменилась цена — `409 price_changed`, нет остатка — `409 sold`. Вещи закрепляются (остаток уменьшается), баллы — не больше 30% стоимости товаров. Отмена до оплаты возвращает вещи и баллы; после оплаты — запрос продавцу.
- **Оплата переводом**: «Перевёл» ставит платёж на ручную проверку и создаёт задачу; подтверждает только сотрудник (повторное подтверждение — `409`). Оплата доставки посылки отдельная. Перевод по заказу, который продавец отменил, пока платёж ждал проверки, подтверждается без возврата заказа в работу: сумма добавляется к возврату (задача «Вернуть оплату»).
- **Заказ по ссылке**: расчёт повторяется на сервере по текущим настройкам (`calcLink` из приложения), цифрам клиента не доверяем. Скидка 50% на комиссию — только с подтверждённой почтой, в первом заказе, не вместе с баллами. Изменение цены продавцом пересчитывает заявку по курсу на момент отправки; до согласия покупателя счёта нет.
- **Очередь задач** строится из состояния, как в приложении: оплаты на проверке, заявки, открытые обращения, фотоотчёты, посылки без трека, отзывы на модерации, заявки на размер, возвраты после отмены; «давно ждёт» — обращения и треки старше 12 часов.
- **Награда за друга**: 250 баллов пригласившему после первого выполненного заказа друга, один раз.
- **Возврат денег** — только по одобренному обращению и только для заказа из наличия; сумма не больше оплаченного за товары; после реквизитов покупателя решение не меняется.
- **Отмена продавцом** (adm30): причина из списка, «Другая причина» — с комментарием; если были подтверждённые оплаты — задача «Возврат» до отметки «деньги возвращены».
- **Счёт за доставку посылки** (adm29): только у оплаченного заказа из-за границы на складе в Китае и дальше, один раз на посылку; без посылок создаётся «Посылка 1» со всеми вещами.
- **Разбиение на посылки** (adm34): только на этапе «На складе в Китае»; от 1 до 4 посылок и не больше, чем вещей; пустых нет, каждая вещь ровно в одной. Посылка со счётом или треком не меняется (`409 parcel_locked`), лишние свободные посылки удаляются. Право «Заказы».
- **Повторное оформление**: `POST /api/orders` и `POST /api/link` принимают `key` — ключ попытки; повтор с тем же ключом возвращает уже созданный заказ (вещи и баллы не списываются второй раз).
- **Пределы покупателя** (`src/limits.ts`, в памяти процесса): загрузки 60/ч, оформление и заявки 30/ч, черновики 120/ч (не больше 20 черновиков по 64 КБ), заявки на размер 20/сут, письма подтверждения 5/ч; сверх — `429 too_many`. Повтор той же заявки на размер возвращает прежнюю. Чек к платежу: платёж проверяется до сохранения файла.
- **Очистка загрузок** (`src/services/cleanup.ts`): при запуске и раз в сутки удаляются загрузки покупателей (чек, фото обращения, отзыва, позиции заявки) старше 7 дней, на которые ничто не ссылается, включая черновики.
- **Удаление аккаунта** — нельзя при незавершённых заказах; данные стираются, заказы остаются для отчётности.
- **Почта** (`src/services/mail.ts`, nodemailer): `POST /api/email` сначала отправляет письмо через ящик магазина и только потом сохраняет адрес (`wait`); ящик не принял — `502 mail_failed`, адрес не меняется. Ссылка `/api/email/confirm?token` действует 24 часа (`email_sent_at`), отвечает страницей: «подтверждена» (200), «устарела» (410, в приложении состояние `err`), «не подходит» (404). Подтверждение включает канал «Почта»; прошлые события письмами не догоняются. Письма о событиях — тем, у кого почта подтверждена и включены канал и категория (`events.mailed_at`), только за последний час; отказ 5xx не повторяется.
- **Сообщения бота** отправляются после ответа, если покупатель разрешил их и включил категорию; без `BOT_TOKEN` события видны только в «Событиях». Проходы рассылки по одному покупателю идут по очереди (без дублей); ответ Telegram 403/400 не повторяется.
- **Живое обновление заказов** (`src/live.ts`): `GET /api/live` — поток `text/event-stream` для вошедшего покупателя или сотрудника. После успешного изменения заказа, оплаты, заявки, обращения, заявки на размер или баллов сервер шлёт сигнал `data: orders` без данных: изменение покупателя — ему и сотрудникам, изменение сотрудника — всем; сигналы за 200 мс склеиваются. Приложение само перечитывает экран обычными запросами с проверкой прав. Каждые 25 с — комментарий `: ping` (меньше `proxy_read_timeout` nginx 60 с), заголовок `X-Accel-Buffering: no` отключает буфер nginx — правка nginx не нужна. Не больше 5 потоков на человека и 2000 всего; при остановке сервера потоки закрываются (`preClose`). Новый изменяющий маршрут заказов добавляйте в `BUYER_ORDER`/`STAFF_ORDER`.
- **Аватарки** (`src/services/avatars.ts`): при входе (не чаще раза в сутки) и после запуска для всех непроверенных сервер берёт фото через бота (`getUserProfilePhotos` → `getFile` → `/file/bot…` через `TELEGRAM_API`) и хранит публичным файлом `avatar`; в ответах — `/files/<id>`, иначе ссылка Telegram из initData (`avatarOf`). Нет фото — файл удаляется; Telegram не ответил — прежняя аватарка остаётся. Без `BOT_TOKEN` и в тестах ничего не скачивается. Где отдаётся: сессия покупателя, покупатели, заказы и все ответы с `buyerPhoto`, сотрудники, журнал (`whoPhoto`), отзывы в админке.
- **Файлы к обращению, отзыву и позиции заявки** — только свои и того же назначения (`claim`, `review`, `link_item`); чужой id — `400`.

## API

Публичные: `GET /api/catalog?f=<json фильтра>&page`, `/api/catalog/facets`, `/api/products/:id`, `/api/search?q`, `/api/showcase`, `/api/rates`, `/api/requisites`, `/api/legal`, `/api/legal/:id`, `/api/reviews`, `/api/system`, `/api/inviter/:tgId`, `/api/email/confirm?token`, `/files/:id`.

Покупатель (`/api`): `POST /session`, `GET|PATCH|DELETE /me`, `GET /live` (поток сигналов), `PUT /me/notif`, адреса, `POST|DELETE /email`, избранное, `GET /events`, `POST /events/read`, `GET /points`, `POST /files?kind=claim|review|link_item`, `POST /checkout/validate`, `POST|GET /orders`, `GET /orders/:num`, `POST /orders/:num/cancel|received|accept`, `GET /orders/:num/photo-report`, `GET /payments`, `POST /payments/:id/receipt|transferred`, `POST /link`, черновики `/link/drafts`, `POST /size-requests`, `GET /claims/:num`, `POST /claims`, `POST /claims/:id/photos|refund`, `POST /reviews`.

Администратор (`/api/admin`): `GET /tasks`; оплаты `GET /payments/:id`, `POST …/confirm|fail|seller-receipt`; заявки `GET /requests/:num`, `POST …/approve|change|reject`; заказы `GET /orders`, `GET /orders/:num`, `POST …/stage|parcels|parcels/:n/track|parcels/:n/bill|cancel|refunded`, `PUT …/parcels { groups }` (adm34); фотоотчёт `GET /photo/:num`, `POST …/upload|send`, `PUT …/items/:i`; обращения `GET /claims/:num`, `POST …/reply|decide|close`; каталог `GET|PUT /items`, `POST /items/upload`, `GET /showcase`, баннеры `POST /banners/upload`, `POST /banners`, `PATCH|PUT|DELETE /banners/:id`, категории; заявки на размер `GET /sizes`, `POST /sizes/:id`; покупатели и баллы; отзывы; `GET|PUT /settings`; сотрудники и приглашения; `GET /journal?who&type` (только владелец); `GET /summary?range`.

## Устройство

- `src/app.ts` — сборка Fastify: CORS, multipart, вход, ошибки, маршруты. `src/main.ts` — запуск.
- `src/live.ts` — живое обновление заказов: подписки, сигнал после изменения, поток `/api/live`.
- `src/auth.ts` — initData, покупатель и сотрудник запроса, `needUser` / `needStaff(perm)`.
- `src/services/` — бизнес-правила: каталог, заказы и оплата, профиль, после покупки, админка; `core.ts` — настройки, журнал, события и бот.
- `src/views/` — сборка ответов в типах приложения (заказ покупателя, виды админки).
- `src/db/` — схема, подключение (Postgres или PGlite), посев демо-данных. `drizzle/` — миграции (`npm run db:generate` после изменения схемы).
- `test/` — тесты API через `inject` на PGlite в памяти.

## Чего ещё нет

- Почтовый сервис не подключён: ссылка подтверждения пишется в журнал сервера.
- Хранение файлов — на диске сервера; для нескольких серверов понадобится объектное хранилище.
- Мониторинга нет. Развёртывание и ежедневные копии — `deploy/README.md` (с 2026-10-08).

Рабочая база без демо-данных: `node dist/admin-cli.js init` (категории и баннеры), `node dist/admin-cli.js owner <tgId|@username>` (первый владелец).
